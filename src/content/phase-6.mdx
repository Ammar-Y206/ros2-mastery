## Robot Description — URDF/Xacro

### The "Why" & The "How" (URDF vs. Xacro)

A robot needs a **machine-readable body**: link masses, joint limits, sensor mounts, collision geometry. **URDF** (Unified Robot Description Format) is the XML format ROS 2 uses. **Xacro** is a macro layer on top — it lets you parameterize, reuse, and compute (e.g. "wheel radius = 0.05, so circumference = 2π·r").

<Callout type="pitfall" title="CRITICAL Pitfall — The Inertial Tag">
If you set a mass of **0** for any link, Gazebo will either crash or your robot will fly into the air. Every moving part (wheels, arms) must have a non-zero `<inertial>` tag with realistic mass and inertia values. Without inertia, the physics engine can't compute forces and the simulation becomes unstable.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The Orientation Trap">
In URDF, cylinders are created along the **Z-axis** by default. To make them look like wheels (lying flat), you must rotate both the `<visual>` and `<collision>` tags by **π/2 (90 degrees)** around the Y axis: `rpy="0 1.5708 0"`. Forgetting this is the #1 reason wheels look like standing pillars in RViz2.
</Callout>

<Callout type="best-practice" title="Best Practice — Mesh Management">
Always use `.dae` (Collada) files for visual meshes and keep file paths relative using the `package://` syntax. Never hardcode absolute paths like `/home/user/models/chassis.dae` — it will break on every other machine.
</Callout>

## ros2_control — The Muscle System

### The "Why" & The "How" (The Ecosystem)

If you write a custom script to talk to a specific motor driver over Serial/USB, your code is "locked" to that hardware. Switch motor brands → your navigation stack breaks.

`ros2_control` provides a **Hardware Abstraction Layer (HAL)**. It separates the *"what"* (e.g. "drive at 2.0 m/s") from the *"how"* (e.g. "send these specific bits over a CAN bus").

<Callout type="pitfall" title="CRITICAL Pitfall — The Real-Time Loop Danger">
The Hardware Interface's `read()` and `write()` functions are executed within a **Real-Time Thread**. Adding `printf()` or `RCLCPP_INFO()` inside these functions is a **blocking operation**. If a log takes 5ms, you have broken a 100Hz loop (10ms cycle). Only do mathematical bit-shifting or memory-mapped I/O in the hardware interface.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Ghost State' Pitfall">
If your hardware interface doesn't update the `state_interface` (encoders), controllers think the robot isn't moving. They will **ramp power to 100%** to compensate, and the robot will launch uncontrollably once it gains traction. Always verify that `read()` returns real encoder data.
</Callout>

<Callout type="best-practice" title="Best Practice — Standardized SI Units">
Always use standard SI units in ros2_control: **Radians** for position and **Radians/Second** for velocity. Never use RPM or Degrees. The controllers, the planner, and the TF tree all expect SI units. Mixing them is a silent bug that causes the robot to drive at 57× the expected speed (360/2π).
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Missing Gazebo Plugins">
If you spawn your robot in Gazebo and the LiDAR produces **no data** on `/scan`, the most common cause is a **missing or misspelled plugin** in your URDF. The `<plugin>` tag must have the exact `filename` (e.g. `libgazebo_ros_ray_sensor.so`) and the `name` attribute. A typo like `libgazebo_ros_laser_sensor.so` (wrong name) will silently fail — Gazebo loads the model but the sensor publishes nothing.

**Best Practice:** Always verify your plugin filenames against the [gazebo_ros_pkgs documentation](https://github.com/ros-simulation/gazebo_ros_pkgs). The exact `.so` filename matters.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Xacro Macro Errors">
If Gazebo crashes on spawn with an XML parse error, it usually means your Xacro has an **unclosed macro** or a **missing property reference**. Xacro errors are notoriously cryptic. Always test your Xacro with `xacro robot.xacro > /tmp/test.urdf` and `check_urdf /tmp/test.urdf` before launching Gazebo. If `check_urdf` passes, Gazebo will accept it.
</Callout>

<Callout type="best-practice" title="Best Practice — Sim vs. Real as a Plugin Swap">
Structure your Hardware Interface so that the Gazebo plugin (`gz_ros2_control`) and the real hardware plugin have **identical joint and interface names**. Then `ros2 launch my_robot bringup.launch.py use_sim:=true|false` swaps ONE `<plugin>` tag, and the entire rest of the stack — Nav2, planners, TF — is identical. This is the **digital twin pattern**.
</Callout>
