## Parameters — Dynamic Configuration

### The "Why" & The "How"

Parameters are configuration values associated with a node. Instead of writing a "Front Left Motor Node" and a "Rear Right Motor Node," you write one "Motor Node" and pass it a parameter indicating its physical location and max speed at startup.

In ROS 2, there is **no central Parameter Server** (unlike ROS 1). Every single node is its own parameter server. When you change a parameter from the terminal, you are actually making a hidden Service call to that specific node's `~/set_parameters` interface.

### Bulk Loading — YAML Configurations

When your autonomous stack grows, you will have hundreds of parameters. You cannot set these one-by-one in the terminal. You use a YAML file namespaced under the exact node name:

<Callout type="how" title="The How — YAML Bulk Loading">
```yaml
# pid_config.yaml
pid_controller:
  ros__parameters:
    kp: 2.5
    ki: 0.1
    kd: 0.05
    max_steering_angle: 0.35
```

Inject the YAML at startup:
```bash
ros2 run my_control_pkg pid_controller_node --ros-args --params-file ./pid_config.yaml
```
</Callout>

### Critical Parameter Pitfalls

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Parameter Not Declared' Exception">
In ROS 2 Humble, if you try to run `this->get_parameter("max_speed")` without calling `this->declare_parameter("max_speed")` first, the node will **instantly crash** with an exception. Always declare your parameters before using them.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Dangling Callback Pointers (C++ Memory Leak)">
If you do not store the result of `add_on_set_parameters_callback` into a class member variable (like `param_subscriber_`), the shared pointer will be destroyed as soon as the constructor finishes. The callback will **silently detach**, and your dynamic updates will magically stop working with no error message.
</Callout>

<Callout type="best-practice" title="Best Practice — Rejecting Bad Data (The Safety Net)">
The `SetParametersResult` is not just a formality. If an engineer types `ros2 param set /pid_controller kp -5.0`, your node must catch that negative value and return `successful = false`. The CLI will literally reject the engineer's command on the terminal screen, and the robot remains safe.
</Callout>

## The Launch System

### The "Why" & The "How"

A production autonomous stack consists of dozens of nodes: LiDAR drivers, camera drivers, IMU filters, localization algorithms, local planners, global planners, and motor controllers. Opening 50 terminals and typing `ros2 run ... --ros-args --params-file ...` is impossible. We need a deterministic, repeatable way to bring up the entire system with a single command.

In ROS 2, the Launch system is written entirely in **Python**. Because launch files are Python scripts, they are Turing-complete — you can use if/else logic, read environment variables, and conditionally launch different nodes based on hardware.

### Real-world Use Cases

- **The "Bringup" Script:** A single `system.launch.py` that starts the perception stack, loads all tuned YAML files, and boots the motor controllers.
- **Topic Remapping:** You download a community LiDAR package that publishes to `/laser_scan`, but your navigation stack expects `/scan`. You use the launch file to silently remap the topic name without touching the C++ source code.
- **Namespacing:** Running two identical robots on the same Wi-Fi network. You use a launch file to push Robot 1's nodes into the `/robot1/` namespace and Robot 2 into `/robot2/` so their topics don't collide.

<Callout type="pitfall" title="CRITICAL Pitfall — Hardcoding File Paths">
Never use `parameters=['/home/ammar/ros2_ws/src/.../config.yaml']`. If another engineer pulls your code on their machine, it will instantly crash because their username isn't `ammar`. **Always use `get_package_share_directory()`** to resolve paths dynamically based on the active ROS 2 installation.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Forgetting to Install Launch/Config Files">
If you put a `.launch.py` or `.yaml` file in your C++ package's `src` folder, `colcon build` will completely ignore it unless you explicitly tell CMake to install it.

- **C++ fix:** Add `install(DIRECTORY launch config DESTINATION share/\${PROJECT_NAME})` to your `CMakeLists.txt`.
- **Python fix:** Add the paths to the `data_files` array in `setup.py`.
</Callout>

Do not write one massive 500-line launch file. Write a `sensors.launch.py`, a `navigation.launch.py`, and a `control.launch.py`. Then, write a master `system.launch.py` that simply includes the others using `IncludeLaunchDescription`. This keeps the architecture modular — each sub-team owns their launch file.
</Callout>

## Debugging and Data Logging (Rosbag2 & RViz2)

### The "Why" & The "How"

When a robot fails in the field, you need a **flight data recorder** (Rosbag2) to replay the exact sensor stream offline, and a **visualizer** (RViz2) to see what the robot's "brain" perceived at the moment of failure.

- **Rosbag2** records every message on every topic to a SQLite database on disk. You can replay it later at the exact original timing.
- **RViz2** is a passive 3D visualizer. It subscribes to standard sensor topics and renders them in an OpenGL window, mapping data against the robot's TF2 coordinate frames.

### Real-world Use Cases

- **Debugging Phantom Braking:** The robot emergency-brakes on an empty track. You replay the rosbag through RViz2 and see that a single noisy LiDAR point bounced off a dust cloud, and the Nav2 local costmap incorrectly inflated it into a concrete wall.
- **Off-Robot Tuning:** You want to tune the DWB critic weights in your local planner. Instead of draining the robot's battery by running it all day, you record one lap. You sit in the lab, loop the bag file, and watch the planner's projected trajectories shift in RViz2 as you mutate the parameters via the CLI.

<Callout type="pitfall" title="CRITICAL Pitfall — The SSD Storage Nightmare">
If your robot has two 4K cameras running at 30fps and you type `ros2 bag record -a`, you will write **gigabytes of uncompressed image data** to your hard drive every few seconds. You will completely fill the robot's SSD mid-operation, causing the OS to crash and the vehicle to stall.

**Best Practice:** Use the `-x` (exclude) flag with regular expressions to skip massive raw images:
```bash
ros2 bag record -a -x "/camera/(.*)/image_raw" -o safe_telemetry
```
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Fixed Frame' Error in RViz2">
This is the #1 reason engineers think their sensors are broken. When you open RViz2, the "Fixed Frame" dropdown defaults to `map`. If your robot is not currently running a mapping or localization algorithm (Nav2/SLAM), the `map` frame does not exist on the network. RViz2 will throw a massive red **"Global Status: Error"** and refuse to render any data.

**Best Practice:** Always change the Fixed Frame to `base_link` or `odom` when doing raw sensor debugging.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Clock Synchronization (--clock)">
If you are playing back a bag file to test an algorithm (like the EKF or a path planner), the algorithm will look at the messages, see a timestamp from 3 days ago, and immediately reject the data as "too old."

**Best Practice:** Run your nodes with `use_sim_time:=true`, and play your bag file with the `--clock` flag. This forces rosbag2 to hijack the ROS network clock and publish the historical time as if it were the present moment.
</Callout>

<Callout type="best-practice" title="Best Practice — The Tuning Loop">
The `-l` (loop) flag is your secret weapon for parameter tuning. Record one lap, then loop it continuously while you adjust PID gains or planner weights via `ros2 param set`. You instantly see the effect in RViz2 without draining the robot's battery or risking hardware damage.
</Callout>
