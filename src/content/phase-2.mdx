# Phase 2: Integrated Communication Protocols

> Master the **language of robotics**. Define the protocols for how the robot 'talks' — from the non-stop stream of LiDAR data to the critical mission commands that must never fail.

**What you will master:**

- Creating robust **Publishers/Subscribers** for continuous telemetry and sensor feeds.
- Designing **Services** for instant, reliable hardware triggers (like resetting an encoder).
- Implementing **Actions** for complex maneuvers with proactive cancellation safety.

---

## The Three Communication Primitives

ROS 2 provides three distinct communication patterns, each engineered for a specific temporal characteristic. Choosing the wrong one is a common architectural failure.

| Primitive | Pattern | Latency | Use Case |
|-----------|---------|---------|----------|
| **Topic** | Pub/Sub | Continuous, fire-and-forget | Sensor streams, telemetry |
| **Service** | Request/Response | Synchronous, blocking | Hardware triggers, configuration |
| **Action** | Goal/Feedback/Result | Asynchronous, long-running | Navigation, manipulation |

---

## Topics — Continuous Data Streams

### The "Why"

Imagine an autonomous mobile robot driving at 30 km/h. The LiDAR is spinning at 10Hz, generating thousands of data points per second. The motor controller needs constant updates on the target velocity.

You cannot use a "Request/Response" system for this. The motor controller shouldn't have to constantly ask, *"What is my speed now? How about now?"* Topics exist to solve the need for **continuous, decoupled, unidirectional data streams**.

- **Decoupled & Anonymous:** A node publishing to a topic has no idea who is listening. A node subscribing to a topic has no idea who is sending the data. They only care about the **Topic Name** (e.g. `/vehicle/speed`) and the **Message Type** (e.g. `std_msgs/Float32`).
- **Many-to-Many:** One LiDAR node can publish to `/scan`. Five different nodes (Mapping, Obstacle Avoidance, Visualizer, Data Logger, Safety Watchdog) can all subscribe to `/scan` simultaneously without bottlenecking the publisher.

<Callout type="how" title="The How — Topic Anatomy">
A topic is defined by three things:
1. **Name** — a URI-like string (`/vehicle/speed`, `/scan`, `/camera/image_raw`)
2. **Type** — a strongly-typed message definition (`std_msgs/msg/Float32`, `sensor_msgs/msg/LaserScan`)
3. **QoS** — Quality of Service profile (reliability, durability, history depth)
</Callout>

### Real-world Use Cases

- **Publishers:** Wheel encoders publishing the current physical velocity; a camera driver continuously publishing raw image frames; an IMU publishing linear acceleration and angular velocity.
- **Subscribers:** The dashboard UI listening to the velocity to display a speedometer; the perception algorithm subscribing to the camera frames to detect obstacles; the Extended Kalman Filter (EKF) subscribing to the IMU to calculate exact vehicle pose.

<Callout type="best-practice" title="Best Practice — Zero-Copy Pointers in C++">
Notice in the C++ subscriber, the callback argument is `const std_msgs::msg::Float32::SharedPtr msg`. We pass by a **constant shared pointer**. For a simple float, it doesn't matter. But if that message is a 15-megabyte PointCloud from a 3D LiDAR, passing by value would cause a massive memory copy, creating a catastrophic CPU spike. **Always use pointers for message callbacks.**
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The Missing Placeholder in C++">
When binding the callback in `create_subscription`, engineers often forget the `std::placeholders::_1`. This tells C++ that the callback function expects exactly one argument (the incoming message). Without `_1`, the code will refuse to compile with a deeply confusing template error.
</Callout>

## Services — Synchronous Requests

### The "Why" & The "How" (Client/Server Architecture)

Topics use a **"fire-and-forget"** broadcast model. If you publish a message to enable the emergency brakes on a Topic, the Publisher has no idea if the motor controller actually received it or acted on it.

For critical, one-off commands, you need a **Request/Response** architecture. You need a guarantee. A Service allows one node (the Client) to send a specific Request to another node (the Server) and pause its own high-level logic until it receives a concrete Response (Success/Failure).

Under the hood in the DDS layer, a ROS 2 Service is actually constructed using **two hidden, paired DDS Topics**:
- The Client publishes to a hidden Request topic with a unique Sequence ID.
- The Server processes the request and publishes to a hidden Reply topic with the same Sequence ID.
- The Client matches the ID, accepts the response, and resumes.

<Callout type="how" title="The How — Service Anatomy">
Unlike Topics, Services are **1-to-1** (or Many-to-1). Only one node can act as the Service Server, though multiple clients can send it requests. This ensures there's a single source of truth for the service's state.
</Callout>

### Real-world Use Cases

- **Resetting the EKF:** If your robot spins out and the `robot_localization` node loses its pose estimation, you don't stream "reset" at 10Hz. You call an `/ekf/reset` service once, and the EKF replies "Reset Complete" so the planner knows it can safely resume navigation.
- **Sensor Calibration Routine:** Triggering the steering servo to sweep from lock-to-lock to find its center before operation begins.
- **State Management:** Changing the state of the PID controller (e.g., toggling it from Active to Inactive) using a boolean flag.

<Callout type="pitfall" title="CRITICAL Pitfall — The Deadlock Trap">
**NEVER use synchronous `client_->call()` (or `client.call()` in Python) inside a timer or subscription callback when using a Single-Threaded Executor.**

Here's what happens if you do:
1. Your timer callback fires and calls `client_->call()` (blocking).
2. The Client sends the request to the Server.
3. The Server processes it and publishes the response to the DDS queue.
4. **The Trap:** The only thread capable of reading that response queue is currently frozen inside your timer callback, waiting for the response! The system is **permanently deadlocked**.

**How Professionals Handle This:**
- **Always use Asynchronous calls** (`async_send_request` / `call_async`): fire the request and immediately exit. Provide a callback that the Executor will run when the response arrives.
- **Callback Groups & Multi-Threaded Executors:** If you absolutely must block and wait sequentially, place the Service Client into a separate `MutuallyExclusiveCallbackGroup` and spin using a `MultiThreadedExecutor` (covered in Phase 5).
</Callout>

When an Action Client sends a goal, it receives a **Goal Handle**. This handle is your direct line of communication to that specific executing task. ### Real-world Use Cases

- **Dynamic Obstacle Avoidance:** Aborting a path-following action because a pedestrian swerved into the robot's lane.
- **Emergency Return:** Canceling an active navigation action to immediately route the robot back to base due to low battery voltage.

        status = future.result().status

        if status == GoalStatus.STATUS_SUCCEEDED:
            self.get_logger().info(
                f'Goal succeeded! Time: {result.total_time_elapsed:.2f}')
        elif status == GoalStatus.STATUS_ABORTED:
            self.get_logger().error('Goal was aborted by server.')
        elif status == GoalStatus.STATUS_CANCELED:
            # We expect this due to our preemption!
            self.get_logger().warn(
                'Goal successfully canceled by planner intervention!')
        else:
            self.get_logger().error(f'Unknown result code: {status}')

        rclpy.shutdown()

def main(args=None):
    rclpy.init(args=args)
    rclpy.spin(SafetyPlannerClient())

if __name__ == '__main__':
    main()`,
    },
  ]}
/>

<Callout type="best-practice" title="Best Practice — Proactive Cancellation Safety">
If a new higher-priority goal arrives (e.g. an obstacle appears mid-navigation), you must **cancel the running goal** before accepting the new one. ROS 2 Actions support proactive cancellation — always implement the cancel callback to safely halt actuators before the new goal takes control. The `cancel_triggered_` guard flag ensures you only send one cancel request, preventing middleware flooding.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Spamming Cancel Requests">
Without a guard flag (`cancel_triggered_`), the feedback callback fires 10 times per second. Each invocation would send a new `async_cancel_goal` request. This can completely choke the middleware with hundreds of cancel requests. **Always use a state flag** to ensure you only send the cancel request once.
</Callout>

<Callout type="pitfall" title="Pitfall — Losing the Goal Handle (Python)">
In C++, the `feedback_callback` conveniently provides the `goal_handle` as an argument. In Python, the `feedback_callback` only receives the feedback message. You **must store `self._goal_handle`** during the `goal_response_callback` so you have a reference to it when you need to cancel later. Forgetting this is a common cause of "I can't cancel my action!" bugs.
</Callout>

<Callout type="pitfall" title="Pitfall — Handling Server Rejection">
Never assume the server will accept your goal. If the robot is currently in an "Emergency Stop" state, the Server might reply with REJECT to your drive command. If your Client code immediately tries to ask for a result on a rejected goal, it will throw a fatal null pointer exception. **Always check if the goal was accepted before proceeding.**
</Callout>

## Choosing the Right Primitive

<Callout type="best-practice" title="Best Practice — Choosing the Right Primitive">
- **Is the data a continuous stream?** → Topic
- **Is it a quick question with one answer?** → Service
- **Does it take a long time and need progress updates?** → Action
- **Do you need to cancel it mid-flight?** → Action (services cannot be cancelled)
</Callout>
