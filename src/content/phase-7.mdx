## Sensor Fusion & State Estimation (EKF)

### The "Why" & The "How" (The Kalman Filter)

No single sensor is perfect. Wheel encoders drift on slippery floors. IMUs accumulate gyro bias. GPS bounces off buildings. The **Extended Kalman Filter** fuses them: it predicts the next state from the IMU, then corrects the drift using the encoders, producing a single **filtered truth** that is better than any individual source.

<Callout type="pitfall" title="CRITICAL Pitfall — The Transform Authority Nightmare">
A coordinate frame (`odom → base_link`) can only have **one publisher**. If both the steering controller AND the EKF publish this transform, the visualizer will **flicker violently** as they fight for authority.

**The Fix:** Disable `enable_odom_tf` in the steering controller and let the EKF be the **sole authority** for the `odom → base_link` transform.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The Non-Zero Covariance Rule">
If a sensor reports **zero standard deviation** (perfect data), the EKF treats it as "Infinite Truth." Any glitch can then cause a mathematical singularity (division by zero) and **crash the node**. Always publish a small, non-zero covariance matrix in your sensor messages.
</Callout>

<Callout type="best-practice" title="Best Practice — Coordinate Frame Alignment">
Ensure the IMU and encoders agree on the forward (+X) axis. Use static transforms to align `imu_link` perfectly with `base_link` to avoid the filter thinking the robot is spinning during straight-line travel.
</Callout>

## Perception & Mapping (SLAM)

### The "Why" & The "How" (SLAM vs. EKF)

You might ask: *"If we have an EKF, why do we need SLAM?"*

- **Local Localization** (`odom → base_link`): Provided by the EKF. High-frequency and smooth, but **drifts** over time. After 500m of driving, the EKF might be off by several meters.
- **Global Localization** (`map → odom`): Provided by SLAM. It uses landmarks (walls, pillars, cones) to **snap** the robot back to its true position on the map, effectively zeroing out the EKF drift.

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Ghosting' Effect (LiDAR Vibrations)">
If the LiDAR vibrates on a weak bracket, the beams wobble. SLAM perceives **moving walls**, resulting in a "ghost map" where walls appear doubled. This makes the map unusable for navigation.

**The Fix:** Use a rigid mount and increase the `minimum_travel_distance` parameter so SLAM only processes scans when the robot has moved a meaningful distance.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The Loop Closure Jump">
When SLAM realizes the robot has visited a location before, it shifts the entire map to align (loop closure). A large jump (e.g., 1m) can **jerk the steering** of a high-speed controller.

**The Fix:** Keep the EKF well-tuned so accumulated drift stays small. This ensures loop closure jumps remain under 10cm — unnoticeable to the controller.
</Callout>

## Nav2 — The Navigation Framework

### The "Why" & The "How" (The Modular Navigator)

An autonomous robot doesn't just need a path; it needs a **strategy**. It needs to know how to get from Point A to Point B (Global Planning), how to avoid a suddenly appearing obstacle (Local Control), and what to do if it gets stuck (Recovery).

Nav2 is the industry-standard modular framework for this. It replaces the old ROS 1 Navigation Stack with a more robust, plugin-based architecture designed specifically for production-grade robots.

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Plan vs Control' Frequency Mismatch">
Planning a 50m path is CPU-intensive. The Pitfall: running the Global Planner at 20Hz. If it takes 100ms to compute, the steering becomes **jerky** because the controller has to wait for the new path.

**Best Practice:** Run the Planner at **1-2Hz** (replan once or twice per second) and the Controller at **20-50Hz** (smooth, reactive control). The BT Navigator handles this automatically via its replanning logic.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — The 'Latching' Trap (Ackermann)">
Default Behavior Trees might try to **Spin** (rotate in place) to recover from being stuck. An Ackermann steering robot **cannot spin in place** — it has a minimum turning radius. The spin command will produce zero motion and the robot will be permanently stuck.

**The Fix:** Replace the default BT's `Spin` recovery with `Wait` or `Replan` logic. Use the `nav2_behaviors` plugin to define custom recovery behaviors that respect Ackermann kinematics.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Footprint vs. Radius">
Never use `robot_radius` for a rectangular robot. A circle over-approximates the corners, causing the robot to avoid gaps it could actually fit through.

**Best Practice:** Define an explicit **Footprint** (list of [x, y] coordinates for the 4 corners) so Nav2 ensures no corner clips a wall. This is especially critical for Ackermann vehicles with long wheelbases.
</Callout>

<Callout type="best-practice" title="Best Practice — Costmap Inflation Tuning">
Walls in a map are single lines of pixels. If a path is planned right next to those pixels, the robot's physical width will cause a collision. The **Inflation Layer** creates a buffer zone. Set `inflation_radius >= robot_radius + 0.1m` safety margin. For tight spaces: tune it to be as tight as possible while still preventing collisions.
</Callout>
