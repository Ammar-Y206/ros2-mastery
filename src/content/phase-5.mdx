## Composition — Component Nodes (IPC & Zero-Copy)

### The "Why" & The "How"

If you launch a Camera Driver Node and a Perception Node using standard `ros2 run` commands, the OS places them in two completely separate physical processes. They cannot see each other's memory.

To send a 15-Megabyte image from the camera to the detector, ROS 2 must: copy the image → serialize it to bytes → push through the OS network loopback → deserialize it → copy it into Node B's memory. At 30 FPS, this **maxes out your CPU** before the algorithm even starts.

**Composition** eliminates this pipeline using **Intra-Process Communication (Zero-Copy)**. Instead of standalone executables, you compile nodes as shared libraries (.so) and load them into a single **Component Container**. Because they share the same memory space, ROS 2 passes a simple memory pointer — **0 bytes copied, 0ms network overhead**.

<Callout type="pitfall" title="CRITICAL Pitfall — SharedPtr vs UniquePtr (The Hidden Copy)">
If your Camera Node publishes a `SharedPtr` and your Perception Node subscribes via `SharedPtr`, ROS 2 intra-process comms will pass the pointer, but it **might still execute a memory copy** under the hood to preserve memory safety (multiple owners could modify the data simultaneously).

To guarantee **absolute zero-copy**, the publisher must publish a `std::unique_ptr` (relinquishing ownership) and the subscriber must accept a `std::unique_ptr`. This proves only one node owns the memory at a time — no copy needed.
</Callout>

<Callout type="best-practice" title="Best Practice — Automate with Launch Files">
No team has the time to manually load shared libraries into a container during operation. Use `ComposableNodeContainer` in your launch file to spawn the master process and pass it a list of `ComposableNode` objects. The Launch Executor handles the dynamic injection automatically:

```python
container = ComposableNodeContainer(
    name='perception_container',
    package='rclcpp_components',
    executable='component_container_mt',  # Multi-threaded!
    composable_node_descriptions=[
        ComposableNode(package='my_sensor_pkg', plugin='robot_sensors::CameraDriverNode', name='camera_driver'),
        ComposableNode(package='my_perception_pkg', plugin='robot_perception::FastPerceptionNode', name='fast_perception'),
    ],
    output='screen'
)
```
</Callout>

## Managed Nodes — Lifecycle Nodes

### The "Why" & The "How" (Deterministic Boot Sequencing)

Standard ROS 2 nodes boot chaotically. If your autonomous path planner boots and publishes a hard-left steering command to `/cmd_vel` **before** the steering motor driver has finished calibration, you risk hardware damage. We must enforce a strict, **deterministic boot order**.

A Lifecycle Node wraps the standard node in a rigid **State Machine**. The node cannot do work until an orchestrator explicitly transitions it through the states.

<Callout type="how" title="The How — The Deterministic Boot Sequence">
With Lifecycle Nodes, the boot sequence is:
1. All nodes boot to **Unconfigured** simultaneously.
2. The Lifecycle Manager calls `on_configure()` on the hardware drivers first → they become **Inactive** (USB ports opened, sensors initialized).
3. Once all hardware is confirmed ready, the Manager calls `on_activate()` on the planners and controllers → they become **Active** (publishing starts).
4. The robot is now safe to operate — no race conditions, no commands before hardware is ready.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Non-Deterministic Boot (The Race Condition)">
Without Lifecycle Nodes, standard ROS 2 nodes boot in a **race condition**. If your path planner boots faster than your motor driver:
1. Planner publishes `cmd_vel: linear=2.0, angular=0.5` (hard left turn).
2. Motor driver hasn't finished calibration yet — it ignores the command.
3. Motor driver finishes calibration, starts listening.
4. Planner publishes `cmd_vel: linear=0.0` (stop).
5. But the motor driver missed the first command and now the robot jerks unexpectedly.

**The Lifecycle pattern eliminates this**: the Lifecycle Manager waits until ALL hardware nodes report `Active` before activating the planner. No race conditions, no jerks, no hardware damage.
</Callout>

<Callout type="best-practice" title="Best Practice — Use the Nav2 Lifecycle Manager">
Don't manually call `ros2 lifecycle set` on 12 nodes. Use **Nav2's `lifecycle_manager`** — it brings up a configured list of nodes in order, with retry logic, and brings them down in reverse order on shutdown. One command, deterministic boot:

```bash
ros2 launch nav2_bringup lifecycle_bringup.launch.py
```
</Callout>
