# Phase 4: Spatial Awareness & Kinematics

> Give the robot a sense of space. Build the **'Digital Geometry'** of the robot — ensuring every sensor knows exactly where it is relative to the world and the chassis, down to the last millimeter.

**What you will master:**

- Managing complex **Coordinate Frames** (`map`, `odom`, `base_link`) to prevent localization errors.
- Solving real-world problems like sensor displacement and wheel-to-LiDAR calibration.

## TF2 — The Transform Framework

### The "Why" & The "How" (Coordinate Frames & The TF Tree)

Sensors are selfish. A LiDAR node only knows the distance of a laser return relative to its own physical glass lens. It knows nothing about the robot. If the LiDAR says *"obstacle at (X: 5.0, Y: 0.0)"*, but the LiDAR is mounted at the very front bumper (2 meters ahead of the rear axle), the obstacle is actually **7 meters** away from the vehicle's pivot point. If we don't translate these coordinates accurately, the robot will steer too early or too late and crash.

**TF2** is a distributed, time-stamped coordinate tracking system. It maintains a **Tree** of coordinate frames. Instead of doing complex 3D matrix multiplication in your head, TF2 handles the heavy lifting. You simply ask: *"What was the transform from `base_link` to `lidar_link` at exactly 0.5 seconds ago?"* and it returns the precise X, Y, Z translation and Quaternion rotation.

<Callout type="how" title="The How — The REP-105 Standard">
To conform to industry standards (REP-105), you must structure your tree exactly like this: **map → odom → base_link → sensor_links**. This hierarchy is not optional — Nav2, SLAM, and robot_localization all assume this structure. Violating it will cause silent navigation failures that are extremely difficult to debug.
</Callout>

### Real-world Use Cases

- **Static Broadcasters:** The LiDAR mount — the distance between `lidar_link` and `base_link` is defined by a metal bracket. It never changes. TF2 broadcasts it once, and subscribers cache it forever, saving massive network bandwidth.
- **Dynamic Broadcasters:** Wheel odometry — as the robot drives, the position of `base_link` relative to `odom` changes 50 times per second. A Dynamic Broadcaster attached to the motor encoders continuously updates this relationship on the network.

<Callout type="pitfall" title="CRITICAL Pitfall — TF2 Time Travel (The Extrapolation Error)">
TF2 is **time-stamped**. Every transform carries the exact time it was measured. If you ask TF2 for the transform at time T, but the latest available transform is from time T-2.0 seconds, TF2 will throw an `ExtrapolationException`: *"Lookup would require extrapolation into the past."*

This happens when a node starts slowly (e.g., a heavy SLAM node takes 3 seconds to boot), but other nodes are already publishing. The late node asks for a transform from 3 seconds ago, but the TF buffer only keeps 10 seconds of history.

**Best Practice:** Always use `tf2::TimePointZero` (C++) or `rclpy.time.Time()` (Python) to request the **latest available** transform instead of a specific timestamp, unless you absolutely need historical data.
</Callout>

<Callout type="pitfall" title="CRITICAL Pitfall — Frame Existence (The Broken Tree)">
If `tf2_echo` fails with *"Could not transform lidar_link to map"*, it means your **tree is broken**. A parent is missing, or a child is detached. The most common causes:

1. **Missing static broadcaster:** You forgot to launch the `static_transform_publisher` for `lidar_link`. TF2 doesn't know `lidar_link` exists.
2. **Node crash:** The `odom_tf_broadcaster` crashed, so the `odom → base_link` edge is gone. The tree is split in two.
3. **Wrong frame name:** Your code asks for `lidar_link` but the broadcaster publishes `lidar_frame`. Case-sensitive!

**Best Practice:** Run `ros2 run tf2_tools view_frames` and open the PDF. If `lidar_link` is floating alone without an arrow connecting it to `base_link`, you instantly know your static transform publisher crashed or was never launched.
</Callout>

<Callout type="best-practice" title="Tech Lead Note — The frames.pdf is Your Best Friend">
When you open `frames.pdf`, it visually maps **every active coordinate frame**, who its parent is, who is broadcasting it, and the average broadcast frequency. If `lidar_link` is floating alone without an arrow connecting it to `base_link`, you instantly know your static transform publisher from crashed. This single PDF saves hours of debugging.
